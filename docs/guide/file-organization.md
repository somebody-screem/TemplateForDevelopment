# ファイルの整頓ルール

| 項目 | 内容 |
| --- | --- |
| この文書に書くこと | ファイルの保存先、名前、依存関係の書き方、整理の手順 |
| 依存先 | なし。このプロジェクトの配置ルールの正本 |
| 関連資料 | [文書一覧](../README.md)、[開発の進め方](workflow.md) |

## 置き場所を決める

| 書きたい内容 | 保存先 | 具体例 |
| --- | --- | --- |
| 製品全体の目的・要求 | `docs/product/` | `vision.md`, `requirements.md` |
| 全体構成・共通の技術的制約 | `docs/architecture/` | `overview.md` |
| 1機能の仕様・設計・作業・検証 | `docs/features/FEAT-NNN-short-name/` | `FEAT-001-task-list/spec.md` |
| 重要な選択肢と選んだ理由 | `docs/decisions/` | `ADR-001-storage-choice.md` |
| 検証中のアイデアと試作コード | `experiments/EXP-NNN-short-name/` | `EXP-001-task-input/README.md` |
| 人間向けの共通ルール | `docs/guide/` | この文書 |
| コピーして再利用する原本 | `templates/` | `feature/spec.md` |
| 書き方の完成例 | `examples/` | 架空のタスクリスト機能 |
| 採用済みのアプリコード | `src/` | 技術スタックを決めてから配置 |
| 自動テストと固定の入力データ | `tests/` | 仕様の受入条件に対応するテスト |
| 廃止文書 | `docs/archive/` | 元のカテゴリとIDを維持する |
| 共有不要の一時ファイル | `.tmp/` | 手元のログや途中の出力。Git対象外 |

画像・図の元データは、その文書と同じフォルダの `assets/` に置きます。複数機能で共有する設計が必要になったら `docs/architecture/` に移し、機能側はリンクで参照します。共有する試作の成果は `experiments/` に保存します。

## 名前とID

- 通常のパス名は英小文字とハイフン、見出しと説明は日本語にする。`README.md`、`AGENTS.md`、`FEAT-001-…`、`ADR-001-…`、`EXP-001-…` は定型名とする。
- 機能・決定・試作の番号は種類ごとに採番する。使用済み最大値の次を使い、廃止後も再利用しない。並行作業で重なった場合は統合前に片方を改番する。
- 機能内の名前は `spec.md`、`design.md`、`tasks.md`、`verification.md` に固定する。
- 文書IDは `FEAT-001-SPEC`、要件IDは `FEAT-001-R01`、受入条件IDは `FEAT-001-AC01` のように記載する。削除した要件IDを別の意味で再利用しない。
- `final`、`latest`、`v2` をファイル名に足して複製しない。更新履歴はGitで管理し、後継の意味が異なる文書だけ新しいIDを与える。
- 文字コードはUTF-8、日付は `YYYY-MM-DD`。期限や実施日時に時刻が必要ならタイムゾーンも書く。

## 文書の冒頭に書くこと

仕様・設計・作業計画・検証記録・決定記録・試作メモには次の表を置きます。READMEや案内文書は、冒頭の説明とリンク表で役割が伝われば十分です。

| 項目 | 記入する内容 |
| --- | --- |
| 文書ID | パスが変わっても意味を追える識別子 |
| 状態 | `下書き` / `有効` / `廃止`。原本は `テンプレート`、例は `記入例` |
| この文書に書くこと | 何を知るための文書かを一文で |
| 依存先 | 内容の前提になる文書への相対リンクと、何を引き継ぐか。なければ `なし` |
| 関連資料 | 参考情報・試作・実装先・反映先など。なければ `なし` |

「依存先」は上流だけにします。`design.md` は `spec.md` を前提にしますが、仕様から設計を案内するリンクは「関連資料」に入れます。見つけやすさのための相互リンクと、内容の相互依存を区別してください。

本文の要求や判断は1か所を正本にします。例えば、受入条件は仕様に置き、検証記録ではIDを参照して結果を書きます。文書と実装が食い違った場合は、依頼内容と合意済みの要件を確認し、どちらを更新するか判断します。

## 状態と未決事項

| 状態 | 意味 |
| --- | --- |
| 下書き | 仮説や検討中の内容。確定仕様として扱わない |
| 有効 | 今回の作業の根拠として採用した内容。実装済み・テスト成功という意味ではない |
| 廃止 | 現在の根拠として使わない。理由と後継を残す |
| テンプレート / 記入例 | 原本 / 説明用の架空例。実際の仕様に含めない |

作成・更新しただけで `有効` にしません。依頼で採用が明確な内容はその根拠を記録して有効にでき、未合意の提案は下書きにします。実装完了は作業計画、検証の成否は検証記録で管理します。`TODO:` は未決、`対象外: 理由` は不要と判断済み、`未実施` は未検証を表します。

## 追加・移動・廃止

1. 文書を追加するときは、[テンプレート](../../templates/README.md)から必要なものをコピーする。ID・状態・依存先を修正し、コピー先からリンクを確かめる。
2. 新しい文書の種類は [docs/README.md](../README.md)、個別機能は [機能一覧](../features/README.md)、個別の決定記録は [決定記録一覧](../decisions/README.md) に登録する。試作は [試作一覧](../../experiments/README.md) に登録する。
3. 移動や改名の前に旧パス・文書IDを検索し、移動するファイル内と参照元の相対リンクを直す。
4. 廃止文書は状態・理由・後継を記載し、`docs/archive/` の元カテゴリ配下へ移す。例: `docs/archive/features/FEAT-001-task-list/`。
5. 現役の仕様が廃止文書を依存先にしていたら、後継へ切り替えるか、必要な内容を有効な文書へ移す。歴史的な参照は「関連資料」とする。
6. [廃止文書一覧](../archive/README.md)に旧パスと新しいリンクを登録する。実装済みで今も使われる機能の仕様は現役のまま残す。

生成物の除外設定は技術選定時に `.gitignore` へ追加します。フレームワークが `app/` やコード横のテストを要求する場合は、この文書と各READMEを更新して配置ルールを合わせます。
