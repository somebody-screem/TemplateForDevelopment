# 開発の進め方

| 項目 | 内容 |
| --- | --- |
| この文書に書くこと | 試作・仕様化・実装・検証をつなぐ手順 |
| 依存先 | [整頓ルール](file-organization.md): 文書の状態と置き場所 |
| 関連資料 | [テンプレート](../../templates/README.md)、[記入例](../../examples/README.md)、[開発コマンド](../../README.md) |

## 必要な文書を選ぶ

| 今回の作業 | 最初に読むもの | 残すもの |
| --- | --- | --- |
| アイデアを動かして確かめる | 製品の目的、関連する要件 | 試作メモ・結果 |
| 新しい機能を作る | 全体要件、関連する全体設計 | 機能仕様・設計・作業計画・検証記録 |
| 既存機能を小さく直す | 既存機能の仕様と検証記録 | 既存文書への差分と検証結果 |
| 誤字や配置だけ直す | 対象文書、整頓ルール | 対象文書・リンクの修正 |
| 共通構成を変える | 全体設計、依存する機能 | 全体設計・必要な決定記録・影響先 |

設計と作業が数行で済む小機能では、仕様の「実装メモ」「作業」節へ統合して構いません。その場合、全体設計・決定記録などへの外部依存を統合後の仕様へ引き継ぎ、作業IDも維持します。検証記録の依存先を仕様の該当節へ修正し、機能一覧にも統合先を記載します。省略したファイルへのリンクを残さず、統合によって依存が循環する場合は分割を維持します。

## 対話・試作から始める

1. [試作メモ](../../templates/experiment.md)を `experiments/EXP-NNN-short-name/README.md` にコピーする。問い・試す範囲・成功条件を短く書く。
2. Codexと試作し、コードと再現手順を同じ実験フォルダへ保存する。未決の前提を仮説として残す。
3. 触って確かめた結果をメモする。「採用」「追加調査」「破棄」の判断と理由を記載する。
4. 採用する振る舞いを機能仕様の要件と受入条件へ移す。試作メモは関連資料としてリンクする。
5. 下記の実装・検証手順へ進み、採用したコードを `src/`、テストを `tests/` へ整理する。

Codexへの依頼例:

```text
docs/product/vision.md と docs/product/requirements.md を踏まえ、
「ここに試したいこと」を小さく試作してください。
templates/experiment.md を使って、問い・仮説・成功条件・結果を残してください。
動かして確かめた内容と、まだ確かめていない内容を分けて報告してください。
```

## 仕様から始める

1. [機能テンプレート](../../templates/README.md)を `docs/features/FEAT-NNN-short-name/` にコピーし、ID・リンクを合わせる。
2. `spec.md` に目的・対象外・要件・受入条件を書く。正常時だけでなく異常時や境界値も決める。
3. 未決事項が今回の実装を妨げるか確認する。依頼から採用内容が明確な場合はその根拠を残す。判断が必要な部分を確認し、独立した部分は進める。
4. `design.md` に構成・データ・失敗時の動作を書く。将来見返す価値のある選択は[決定記録](../decisions/README.md)に残す。
5. `tasks.md` を小さな作業に分け、各作業が満たす受入条件と確認方法を明記する。

Codexへの依頼例:

```text
docs/product/requirements.md を根拠に「ここに機能名」の仕様を作り、
合意済みの範囲を設計・実装・検証まで進めてください。
templates/feature/ を利用し、未決事項は記録してください。
受入条件と検証結果の対応を verification.md に残してください。
```

## 実装・検証する

1. 仕様と設計に沿って小さく実装する。新しい判断で仕様が変わる場合は文書にも反映する。
2. 受入条件に対応するテストや手動確認を実施する。実行コマンドはルートREADMEの設定を確認する。
3. `verification.md` に受入条件ID・確認箇所・実行日時・対象の版・結果を記録する。失敗や未実施もそのまま残す。
4. 検証できた作業を `tasks.md` で完了にする。コードを書いただけで検証済みにしない。
5. 上流文書を変えた場合は、[依存先の探し方](../README.md)に沿って影響先を確認する。

## 今回の変更を完了にする条件

- 今回の範囲と対象外が仕様からわかる。
- 仕様・実装・テストの対応が受入条件IDで追える。
- 必要な検証が完了し、結果を記録した。実施できなかったものがあれば理由と残作業を明示し、検証完了として扱わない。
- 文書の依存先と索引のリンクが有効で、原本や例を確定仕様と混同していない。

## Codex向け指示を調整する

ルートの [AGENTS.md](../../AGENTS.md)に、リポジトリで共通する作業指示をまとめています。製品の詳細は該当文書に置き、そこへの案内を短く保ちます。`AGENTS.md` をプロジェクトの指示として利用する仕組みは[OpenAIの公式ドキュメント](https://learn.chatgpt.com/docs/agent-configuration/agents-md)を参照してください。このフォルダ分けと文書形式は、このテンプレート独自の運用です。
